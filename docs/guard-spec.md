# Guard — who a rule's failure actually stops

**Status:** **Reopened 2026-08-12 — runs must not be user-specific, and the current implementation makes them so.** Core mechanics, CRUD, backoffice authoring surface, real per-user context, and role-scoped rules were all built the same day (see the build checklist), but resolving `Response` *while building each run* (`ContentCheckResolutionService`, while it builds each `ResolvedContentCheckRule`) ties a run's enforcement outcome to whoever happened to trigger that particular run. Worked through directly: a check's result (`Pass`/`Fail`/etc.) is a fact about the content, true for anyone who looks at it; whether a `Fail` actually blocks is a fact about the person about to publish, decided fresh at that moment, never baked into a stored run. The corrected shape — below, superseding the "How the two combine" section as originally written — moves `Response` resolution out of the run entirely and into the publish gate, reading a stored run rather than an inline one. **Not yet re-implemented against this correction** — the build checklist's `[x]` items reflect the pre-correction design; treat them as "built, but the wrong shape" until a follow-up pass moves the resolution call from `ContentCheckResolutionService` to the (still unbuilt) publish-gate handler in [Triggers](triggers-spec.md).
**Part of:** [Overview](overview.md). Extends [Policy Resolution](policy-resolution-spec.md)'s rule model; feeds the blocking decision [Triggers](triggers-spec.md) makes at publish time.

## The problem this solves

A policy rule today has one `Mode`, set once by whoever writes the rule, and it applies everywhere the rule's policy reaches — every content type, every location, every editor, with no way to be stricter for one team and looser for another. There's no way to express "this matters more under `/news` than elsewhere" or "trust senior editors to publish through a warning; block everyone else on the same issue."

## The model

Two separate jobs, owned by two different people, that only meet at save/publish time.

### 1. Requirement Level — set on the rule, by the rule author

Replaces `ContentCheckRuleMode`. Describes how important a failing check is, not what happens when it fails:

| Level | Meaning |
|---|---|
| `Optional` | A nice-to-have. Safe to ignore. |
| `Recommended` | Should be fixed, but isn't a hard requirement. |
| `Mandatory` | Must be fixed. |

This lives on `ContentCheckPolicyRule`, same place `Mode` lives today. The rule author is stating a fact about content quality, not making an enforcement decision — that decision is deliberately not theirs to make.

### 2. Guard — set per section, by whoever owns that section

A new persisted entity, backoffice-authored, the same shape as a `ContentCheckPolicy` (a start node, resolved by nearest-ancestor the same way policy scoping already works — see [Policy Resolution](policy-resolution-spec.md)). Instead of holding checks, it holds a list of `GuardRule`s, each naming the lowest `RequirementLevel` that blocks for a user, a role, or everyone else:

```
(User | Role | catch-all) → BlockAt: RequirementLevel? (null = never block)
```

A rule targets at most one of user/role; when both are `null` it's the catch-all. Most specific match wins — user rule beats role rule beats catch-all. A failing rule blocks only if its `RequirementLevel` is at or above the matched rule's `BlockAt`.

### Runs are never user-specific — corrected 2026-08-12

A check's result is a fact about the content: the same `Fail` shows up for every viewer, cached and reused regardless of who's asking. Nothing about *running* a check — resolving policies, evaluating rules, caching results — should ever consult Guard or take a `currentUserKey`. `IContentCheckResolutionService.ResolveAsync`/`IContentCheckEvaluationService.EvaluateAsync`'s `currentUserKey` parameter and `ResolvedContentCheckRule`/`ContentCheckReportEntry`'s `Response` field are the mistake this correction removes — they made a run's outcome depend on whoever triggered it, so the same content could show `Block` for one viewer and `Warn` for another from the exact same stored report.

### How the two combine — only at the publish gate, never inside a run

1. A run produces (and, per [Core Contract](core-contract-spec.md) §5, caches) a report of what's true about the content: every rule's `RequirementLevel` and result, for everyone. This is the *only* thing a run is responsible for.
2. When someone attempts to publish, [Triggers](triggers-spec.md)'s gate reads the most recent completed run matching the content as it currently stands — it does not run checks itself, and it does not use a report resolved for anyone else's earlier click.
3. For every `Fail` entry in that stored report, the gate resolves Guard **fresh, at that moment, for the person clicking publish right now** — walk up to the nearest Guard for the content's location, find the rule matching this user (user → role → catch-all), and check whether the failing entry's `RequirementLevel` is at or above that rule's `BlockAt`.
4. If any failing entry resolves to blocked for this user, the publish is rejected. If none do, it proceeds — even if the exact same report blocked a different person a moment earlier.

**This is deliberate, not an edge case to guard against.** An editor can see a real `Fail`, get blocked, and hand the same content to an admin whose Guard has a higher (or no) `BlockAt` for that level — the admin publishes successfully, looking at the identical failing check. The check never got easier; only whether *this* person is trusted to publish past it changed. That asymmetry is the entire point of separating Requirement Level (a fact about the content) from Guard (a decision about the person).

**No Guard for a section is a safe default, not a special case to code around.** It means the section behaves exactly as if every rule's `BlockAt` were `null` — nothing blocks, but every check still ran and its result is still visible (on-demand, in the context app, in whatever reporting surface reads results today). This is the whole reason no seeding step or fallback record is needed anywhere in the tree: never-blocking is already what "nothing configured" should mean, so there's no gap for a missing Guard to fall into.

## Build checklist

**The five items below are built, but in the shape the 2026-08-12 correction rejects — `Response`/`currentUserKey` resolved inline, inside a run, rather than at the publish gate. Kept checked as a record of what exists in code today; do not take them as confirmation the design is settled.**

- [x] `RequirementLevel` (`Optional`/`Recommended`/`Mandatory`) replaces `ContentCheckRuleMode` on `ContentCheckPolicyRule`, `ResolvedContentCheckRule`, `ContentCheckReportEntry`, and every Web API model/mapper (`PolicyRuleModel`, `ApplicableRuleResponseModel`) that carried it. **Still correct under the correction** — Requirement Level is a fact about the rule, not the run.
- [x] `ContentCheckResponse` (`Warn`/`Block`) added to `ResolvedContentCheckRule` and `ContentCheckReportEntry`, resolved rather than authored. **Superseded** — a run should never carry a resolved `Response` at all; see the new checklist items below.
- [x] `Guard`/`GuardRule` entities, `IGuardRepository` + `InMemoryGuardRepository`, and `IGuardResolutionService` + its default implementation (nearest-start-node match, user-rule-beats-role-rule-beats-catch-all-rule, `BlockAt` threshold). **The entities and resolution service are still correct** — only *when* they get called needs to move.
- [x] `ContentCheckResolutionService` calls the resolution service while building each `ResolvedContentCheckRule`, so `Response` is already resolved by the time the runner sees a rule. `IContentCheckResolutionService.ResolveAsync` and `IContentCheckEvaluationService.EvaluateAsync` both gained an optional `currentUserKey` parameter to carry this. **This is exactly the mistake the correction removes** — see below.
- [x] `ContentCheckRunner`'s short-circuit and `ContentCheckAggregateReport.HasBlockingFailure` key on `Response == Block`, not a raw level — unit tests updated and passing (`ContentCheckRunnerTests`, `ContentCheckEvaluationServiceTests`, `ContentCheckResolutionServiceTests`), plus new coverage for the resolution service itself (`ContentCheckGuardResolutionServiceTests`). **`HasBlockingFailure` in particular needs to leave `ContentCheckAggregateReport` entirely** — a stored report has no fixed answer to "does this block," only "did this fail," since the answer depends on who's asking, later, at publish time.

**New work the correction requires — none of this exists yet:**

## Considered and rejected

- **Resolving `Response` inline while a run is built (the original implementation, 2026-08-12).** Rejected on the same day it was built, once walked through directly: it makes a run's outcome depend on whoever happened to trigger it, so the exact same stored report reads as `Block` for one viewer and `Warn` for another — a check's result stopped being a fact about the content and became a fact about the request. The fix is to never resolve `Response` inside a run at all; see "Runs are never user-specific" above.
- **Gate rule execution itself on a Guard existing ("no Guard → rule doesn't apply at all").** Rejected — conflates two different questions. Whether a check runs is a policy/scoping decision (start node + content type, already solved). Whether its failure stops anyone is an enforcement decision. Folding "no Guard" into "don't evaluate" would make a section's checks silently vanish from every report just because nobody set up enforcement for it yet — the context app and any on-demand run would go quiet with no error, which is a worse failure mode than always running and never blocking.
- **Seed a mandatory, undeletable default Guard at the site root on install.** Considered as a way to guarantee "no Guard" never actually happens. Rejected once the simpler rule above existed: since "no Guard" already means "everything warns," there's no unsafe gap a seeded default would be protecting against, and a locked, undeletable record is one more thing to build, document, and explain when someone asks why they can't delete it.
- **Treat a rule's `Mode`/`RequirementLevel` as the enforcement decision directly (today's model).** Rejected — this is the premise the whole doc exists to move past. It gives the rule author control over who gets blocked, when the actual differentiator (trust, team, seniority) is knowledge the rule author doesn't have.
- **Name the Requirement Level field "Severity."** Rejected as too abstract for a backoffice-facing field — doesn't read naturally in a sentence the way `Optional`/`Recommended`/`Mandatory` do.
- **Name the Guard-side mapping "Reaction."** Replaced with **Response** — same meaning, reads better paired with `RequirementLevel`.
- **Call the new entity something other than "Guard"** (e.g. "Response Policy," "Escalation Policy"). Rejected — "Policy" is already a specific, different noun in this codebase (`ContentCheckPolicy`, the thing that holds checks); reusing it for this would collide. "Guard" is kept because it's a short, accurate word for the job and doesn't collide with anything existing.

## Open questions

- **Nearest-ancestor tie-break is implemented, but by path-length depth, not by re-checked against [Policy Resolution](policy-resolution-spec.md)'s own tie-break code.** `ContentCheckGuardResolutionService.StartNodeDepth` picks the guard whose start node has the longest resolved path as "nearest" — a reasonable proxy, but never diffed against how policy start-node scoping itself breaks ties, so the two could still disagree on an edge case (e.g. two guards whose start nodes sit at the same depth on different branches).
- **[Core Contract](core-contract-spec.md) and [Triggers](triggers-spec.md) haven't been updated to reference `RequirementLevel`/`ContentCheckResponse` by name.** The code itself has moved (see the build checklist above); the prose in those two specs still describes the old `Mode`/`Blocking` model. Triggers' `Free`-cost restriction on blocking still holds either way (the gate scopes down to cheap checks by cost, not by enforcement mode) but its wording needs a pass once the on-publish handler is actually written.
- **Where Guard is authored in the backoffice — decided and built 2026-08-12.** Lives in the same Checks section as policies (a sibling tree, per [Management API & UI](management-api-ui-spec.md)), not moved into Settings — but only visible/editable for users who also have access to the Settings section, as a proxy for "trusted admin." Deliberately a shortcut, not a real permission: a site could plausibly want someone who manages policies but not enforcement, or the reverse, and Settings-section access doesn't distinguish that. Revisit with a dedicated permission if that gap actually bites; not worth building ahead of a real need.
- **Role/user targeting mechanics — resolved 2026-08-12.** Roles are Umbraco user groups, referenced by `GuardRule.RoleKey`. Ties within the same specificity (e.g. two matching role rules) resolve to whichever rule is listed first on the guard — simple and undocumented anywhere else, revisit only if it actually causes confusion.
