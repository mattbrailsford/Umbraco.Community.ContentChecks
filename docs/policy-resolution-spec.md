# Policy Resolution — attachment, composition, cascading, Effective Checks

**Status:** Design settled (2026-08-05/06), after several rejected intermediate ideas — recorded here rather than dropped, because the reasoning that killed each one is worth keeping. **Phase 2 built (2026-08-06).** Resolution service (direct/composition/cascading match), Effective Checks computation, and the Block List/Block Grid element sources are implemented and unit-tested; EF Core persistence (`Persistence` + `Persistence.SqlServer` + `Persistence.Sqlite`) is live, replacing the in-memory default. One deliberate consolidation beyond what this doc originally implied: `ContentCheckPolicy` and `ContentCheckPolicyFolder` share a single repository and a single `IContentCheckPolicyService`, not two separate ones per entity — a folder has no lifecycle independent of the policy tree it organizes, so splitting them added surface area without buying anything. Real gaps still open, not yet built: tests run against mocked `IContentType`/`IContent` throughout, not a real one (mirrors [Core Contract](core-contract-spec.md)'s own Phase 1 gap); §4's folder delete-with-children question is still unconfirmed and unimplemented (plain delete, no children check); Deploy's refresher handlers ([Notifications](notifications-spec.md) §2–3) aren't built, since Deploy Integration is a later phase.
**Part of:** [Overview](overview.md). Builds entirely on top of [Core Contract](core-contract-spec.md) — the runner there is used unchanged; nothing here reworks it.

## 1. Checks reach inside blocks by attaching to Element Types, not by addressing into a result

Prompted by asking what block-level checking is actually *for* before building addressing machinery to support it.

**The real driver is reusable content components.** Block editors exist so a small library of Element Types (Testimonial, Feature Card, CTA, Hero) can be reused across many document types. A rule like "every Testimonial needs a quote and an author" is a property of the *Testimonial element type* — not of any page that happens to embed one. Checks that could only attach to document types would force that rule to be duplicated into every page type that might contain a Testimonial, or force a page-level check to understand Testimonial's internals directly, defeating the point of Testimonial being an independent, reusable unit. Nested block lists (a Feature Grid block containing a "features" Block List of Feature Card blocks) are the ordinary shape of a real component library, not an edge case — "every Feature Card needs an icon" should fire no matter how many layers of blocks it's sitting under. This also directly serves the AI story: an agent assembling a page from Hero + Feature Grid + Testimonial blocks needs the *same* quality bar applied to each block it generates, regardless of which page it lands on — attaching rules to the element type gives the agent's generate-check-iterate loop that consistency for free.

**Mechanism: Umbraco already unifies the seam we need.** A Document Type and an Element Type are the same underlying `IContentType` in Umbraco Core, just flagged `IsElement`. So "a check policy attaches to a content type" already covers both without inventing a new attachment concept — a policy can target `landingPage` the document type exactly the way another targets `testimonial` the element type.

**Resolution, not the runner, does the tree-walking.** Running checks on a document means two things: run the document's own policies against the document's snapshot, and separately walk every element-holding property, recursively, to any depth, and for each nested element instance found, run *that element type's* policies against *that element's own snapshot*. This is why `IContentCheck.EvaluateAsync` never needs to know about nesting at all — it always receives a snapshot of exactly one thing, root document or one block, and evaluates it identically either way (`snapshot.HasProperty("icon")` reads the same regardless of what it's a snapshot of). `IContentCheckTarget.PropertyAlias` stays unambiguous for the same reason — it's always relative to whatever snapshot the check was actually handed.

**"Element-holding property" is not just Block List/Grid — this has to be pluggable, not hardcoded.** Corrected from an earlier draft that leaned on Nested Content as the motivating second case — Nested Content is obsolete, not "still genuinely common," so it's not pulling its weight as the example. The underlying point stands regardless of that one example: the property editor system is fully open, and nothing guarantees Block List and Block Grid stay the only editors that ever hold element-type content — a future Umbraco release, or a custom/third-party editor on some specific site, could introduce another one at any time. Building the traversal to assume exactly two known editors would mean rewriting it the day a third one matters, instead of the site (or a later version of this package) just registering a new source. So traversal goes through an extension point — an `IContentCheckElementSource`-shaped abstraction, keyed by property-editor alias (which every property already carries), registered the same auto-discovered way `IContentCheck` itself is (attribute + collection builder) — that answers two questions for one specific editor: at design time, which element types a property's configuration allows (needed for §3's Effective Checks computation), and at runtime, which actual element instances a property's stored value contains (needed for this traversal). Ship built-in sources for Block List and Block Grid, the two current, actively-used editors; a site still running Nested Content, or anything else, registers its own — v1 doesn't need to ship one for a deprecated editor to prove the abstraction works. (RTE-embedded blocks likely share Block List's underlying data shape and may need no separate source — verify against actual Umbraco source when this is built, not asserted now.)

**`IContentCheckSnapshot` needs no changes.** A nested block's data (its own `Key`, its own element-type alias, its own property values) fits the existing interface ([Core Contract](core-contract-spec.md)) exactly as it stands — an adapter over Umbraco's block item data is no different in shape from an adapter over `IContent`.

**Phase 1's runner is unaffected — this is additive here, not a rework.** `IContentCheckRunner.RunAsync` already only ever deals with one snapshot and one set of resolved rules ([Core Contract](core-contract-spec.md)); that was already correctly scoped. The tree-walk lives in this resolution layer, which calls the same simple runner once per discovered snapshot (root, then each nested element) and aggregates the individual reports. The ancestor chain — which root property, which chain of block keys — is something the resolution layer has for free at the moment it discovers each element, and is where it belongs: stamped onto whatever aggregate/report structure the UI needs, not constructed by a check author by hand. Exact shape deferred until [Management API & UI](management-api-ui-spec.md)'s actual deep-linking need is real, same discipline as everything cut in [Core Contract](core-contract-spec.md)'s cuts table — design it against the real UI need, not a hypothetical now.

**Real cost consideration this surfaces, not to be decided by accident:** if an element-type check is `Metered` (finding N), a page with twenty Testimonial blocks means twenty evaluations of that check, not one — cascading multiplies `Metered` calls by instance count. Recorded as open question 7 in the [Overview](overview.md); this phase needs a deliberate stance (batch, cap, or accept the cost), not a default that falls out of the implementation.

## 2. Policies are 1:1 to a content type; composition resolves dynamically

Worked through what setting a policy up actually looks like from a content architect's chair. This section replaces several intermediate ideas that came up and were rejected along the way; the rejected ones are recorded here rather than silently dropped, because the reasoning that killed each one is worth keeping.

**A `ContentCheckPolicy` targets exactly one content type, plus an optional start node.** Not a list of many types on one policy — one type, one policy record. `ContentCheckPolicy { ContentTypeKey, StartNodeKey? }` (name/alias/rules as already defined). This is simpler to author and simpler to reverse-lookup ("which policies target type X") than a multi-type list, and it doesn't cost anything: nothing stops *several* separate policy records from targeting the same type with different start nodes — see the layering example below.

**Stored as `ContentTypeKey` (the content type's Guid), not `ContentTypeAlias` — corrected after an earlier draft got this wrong.** An alias is a renamable label, not a durable identity — a developer can rename a Document Type's alias in the editor the same way they can rename its display name. If the policy's own reference were the alias string, a rename would leave it silently pointing at nothing: no error, no notification, just a policy that quietly stops matching anything. That's exactly the kind of invisible governance failure Effective Checks (§3) exists to prevent, just triggered by a rename instead of a composition edit. The content type's Key never changes for the life of that type, which is the correct thing to persist — the same Id/Key/Alias distinction that already drove the `ElementKey` naming in [Core Contract](core-contract-spec.md), applied here too.

**This doesn't change what a check ever sees.** `IContentCheckSnapshot.ContentTypeAlias` ([Core Contract](core-contract-spec.md)) stays exactly alias-typed — a check thinks in alias terms and only ever reads it during one evaluation, never stores it, so there's nothing to go stale. The resolution service resolves `ContentTypeKey` → the type's *current* alias at evaluation time and hands the check that; the Key never leaves the persistence/resolution layer. Authoring UIs ([Management API & UI](management-api-ui-spec.md)) let a developer search and pick a content type by its friendly name/alias as normal — the picker just stores the underlying Key once something's selected, the ordinary "friendly display, durable storage" split.

**Composition resolves dynamically, automatically, transitively — this was tried as an explicit opt-in "include" mechanism first, and rejected.** The alternative considered: a policy attached to a composing type (e.g. Blog Post) would explicitly reference another policy (e.g. one attached to the SEO composition) to pull its rules in — fully predictable, fully visible on the referencing record, no runtime graph-walking. Rejected because it trades away the entire point of attaching to a composition in the first place: the low-friction case — attach a policy to SEO once, done, it reaches every composing type — is what most people actually want, and "include" would make that the *unavailable* path, forcing per-type wiring for something that should just work. So: a policy attached to content type X matches any type that IS X, or that composes from X, directly or transitively (walking Umbraco's live composition graph — `IContentType` doesn't distinguish "document type" from "composition," so this needs no new attachment concept, same as element types in §1). A start node on a composition-level policy still applies as normal — "SEO rules apply everywhere composition reaches, but only under `/blog/`" is expressible on the same record, no tension between the two mechanisms.

**This makes the composition-only-type picker problem from earlier moot, not solved — worth being precise about the difference.** At one point, the concern was that an element type used purely as a composition (never instantiated, never used as a block) would be an invisible dead end if attachment only matched by direct type equality or by nested-block discovery — picking it in a UI would silently produce a policy that never runs. The fix on the table at the time was detecting composition-only types and expanding the selection into their concrete composing types at authoring time. That whole detection-and-expand mechanism is now unnecessary: with composition resolution restored and dynamic, attaching a policy directly to a composition-only type works correctly and automatically reaches every composing type, exactly as a developer would expect. **Do not build the composition-only-detection mechanism** — it was the right fix for a model this plan no longer uses.

**Multiple policies on the same governance area combine by simple union — no relationship between the records needed.** A broad, unscoped policy on SEO ("every composing type needs `metaTitle`") and a narrower policy 1:1 on Blog Post with its own start node (say, stricter `metaDescription` length, only under `/blog/archive/`) both apply to an archived blog post simultaneously. Blog Post's own policy doesn't need to reference SEO's, or know it exists — `metaDescription` is just a property Blog Post's snapshot has, courtesy of composition, and `ContentCheckTarget.PropertyAlias` was never aware of where a property came from ([Core Contract](core-contract-spec.md)). This is the general case, not a special one: composition-wide baseline + type-specific refinement is exactly what independent, unioned, non-referencing policies already give you.

**Context refinement (property + containing type) stays cut.** The scenario that seemed to need it — a generic, heavily-reused element type (a generic Rich Text block) wanting different rules depending on where it's placed — turned out to already be covered by tree-path scoping alone: two separate policies on the same element type, different start nodes, resolve correctly against whichever root document contains the matched instance, regardless of nesting depth. The one case tree-path genuinely can't reach — two instances of the *same* element type on *one* page, at the *same* path, needing different rules from each other — isn't treated as a policy problem: a policy targets a category of content, not one specific instance sitting next to an identical-looking one, and the idiomatic Umbraco answer to "these two things need different rules" is to give them different element types, not to make policy attachment instance-aware.

## 3. Effective Checks is load-bearing, not optional polish

Dynamic composition-matching plus §1's cascading means the set of checks governing a type can change because of an edit somewhere completely unrelated to any check policy — someone adds a composition to a Doc Type, or adds an allowed block to a Block List config, and a `Blocking` check now applies where it didn't yesterday. The only thing that makes this safe rather than surprising is being able to see it.

Effective Checks for a content type is computed at schema/design time — **no live content needed** — by walking:

- the type's own composition ancestry (direct policy matches, transitively), and
- every element-holding property's allowed-element-types configuration (§1, via the pluggable element-source abstraction), recursively through however many levels of nesting the allowed types themselves permit.

Each row needs its provenance labeled plainly, because the three mechanisms are genuinely different things happening at different snapshot levels, not shades of the same "inherited" idea:

- **Direct** — policy targets this type exactly.
- **Via composition `[X]`** — policy targets a type this one composes from. Runs against this type's *own* snapshot, since composition flattens properties onto the root — no nesting involved.
- **Via nested element `[Y]` in property `[Z]`** — policy targets an element type discoverable inside this type's own block structure. Runs against a separate, nested snapshot.

**Presentation, sketched — see [Management API & UI](management-api-ui-spec.md) for the build detail:** a Content Checks backoffice section for authoring policies (content-type picker — one type, doc type or element type — start node picker, rules list with schema-driven config forms per [Core Contract](core-contract-spec.md)); an Effective Checks read-only view, ideally surfaced directly on the Doc Type/Element Type editor (a bigger integration than anything else in this project — extending a core Umbraco editor rather than building inside this package's own section — with a fallback of hosting the same computed view inside Content Checks' own section if that proves too invasive to core UI).

## 4. Folder organization for the backoffice tree

Prompted by a UI requirement, not a resolution-model need: policies should be organizable in the backoffice the way Data Types/Document Types/Media Types are — a tree, with folders an editor creates to group related policies. See [Management API & UI](management-api-ui-spec.md) for the tree/UI build; this section only settles the data model, since folders are a persisted entity `ContentCheckPolicy` itself now references.

**Researched before designing this, same discipline as everywhere else in this project.** Checked both sibling monorepos directly rather than assuming a generic Umbraco pattern applies:

- **Umbraco.AI has no folder concept anywhere.** Profiles, Connections, and Guardrails are all flat `entityContainer`/`collection` list views in the backoffice — no tree manifest, no `ParentKey`/`IsFolder` field on any model. Not a usable precedent for this.
- **Umbraco CMS Core's own native pattern** (`EntityContainer`, `FolderTreeControllerBase<T>`, `EntityTreeControllerBase`, used by Data Types/Document Types/Media Types) is real, but built for *native* CMS entity types with their own container-object-type registration system — a heavier fit than a small third-party EF entity needs.
- **Umbraco.Automate's `WorkspaceGroup` is the directly transferable shape**, because it solves the exact same problem: a custom, EF-backed entity (`Automation`) needing folder organization in its own tree, built without the native CMS base classes at all. Its shape: a distinct `WorkspaceGroup` entity (`Id`, `Name`, nullable `ParentId` for nesting, a back-reference to its owning workspace), a nullable `GroupId` on `Automation` itself, dedicated folder CRUD controllers (`CreateWorkspaceGroupController`, `UpdateWorkspaceGroupController` handling both rename *and* move through one endpoint, `DeleteWorkspaceGroupController`, `AllWorkspaceGroupController` for listing a folder's children), and — moving an automation into a folder is *not* its own endpoint, just the `GroupId` field on the automation's normal update call. The frontend rides Umbraco's native tree *contracts* (`UmbTreeDataSource`, `UmbDefaultTreeElement`/`UmbDefaultTreeContext`) without the backend needing the native tree/folder controller base classes at all — proving that combination works for a third-party EF entity, which is exactly this project's situation.

**Adopted, with one deliberate naming deviation.** `ContentCheckPolicyFolder` mirrors `WorkspaceGroup`'s shape exactly — separate entity, self-referencing nullable parent, no cascading discriminator on the main entity. The one change: this project's own established convention (the Id/Key/Alias discipline that already drove `ContentTypeKey`/`StartNodeKey` in §2) means the durable identifier and the self-reference are named `Key`, not `Id`/`ParentId` the way Automate's actual code has them — a folder's `Name` is exactly as renamable as a content type's alias, so anything referencing it durably needs the same discipline applied consistently, not an exception because the precedent happened to use a different word.

```csharp
public sealed class ContentCheckPolicyFolder
{
    public Guid Key { get; init; }
    public required string Name { get; set; }
    public Guid? ParentFolderKey { get; set; }   // null = root
}
```

`ContentCheckPolicy` (§2) gains one nullable field: `Guid? ParentFolderKey { get; set; }` — null means "at the root," exactly like `WorkspaceGroup.ParentId` and `Automation.GroupId`. Moving a policy into or out of a folder is not a separate endpoint, same reasoning as Automate: it's just this field on the policy's own normal update call.

**Fires its own CRUD notifications, not folded into the policy's.** See [Notifications](notifications-spec.md) §3 — same reasoning `WorkspaceGroup` already validates: a folder is its own persisted entity with its own lifecycle, independent of whatever policies happen to live inside it at any moment.

**Also needs Deploy support, same reasoning as the policy itself.** A folder is schema-level organizational config, no different in kind from the policy it contains — see [Deploy Integration](deploy-integration-spec.md) §4, updated to cover both entities.

**Open, not decided: delete-with-children behavior.** Automate's `DeleteWorkspaceGroupController` cascades — deleting a folder deletes every child folder and automation underneath it. That's a reasonable default for automations; it's a heavier default for check policies, which govern real publish-blocking behavior — silently deleting a dozen policies because someone deleted their containing folder is a bigger footgun here than losing some automations. **Recommendation: block delete if the folder has children** (policies or subfolders), requiring an editor to empty it first — mirrors how Umbraco's native Data Type folders behave, safer than cascading, at the cost of one extra step. Not yet confirmed.

## 5. Phase 2 — Build checklist

**Decided:** check *types* registered in code (like Umbraco.AI providers); check *policies* stored in the DB and authored by editors through the UI (like Umbraco.AI connections/profiles). Editors define which checks apply and how — a code-first v1 would make that a v2 promise, and the whole point of this package is that content people, not developers, own the rules. **Confirmed as the right split by research** — see [research.md](research.md) — Preflight and Drupal Field Validation both land here independently.

- [x] Needs EF Core + SQL Server + SQLite migration projects — three extra projects, biggest scope item in the project. Follows the Umbraco.AI persistence layout (`Persistence`, `Persistence.SqlServer`, `Persistence.Sqlite`), migration prefix `UmbracoCommunityContentChecks_`. Shares the host site's own connection (`shareUmbracoConnection: true`) — no per-product connection-string override, per the Overview §1 sizing call.
- [x] **`ContentCheckPolicy` model, 1:1 to a content type (§2):** alias, name, `ContentTypeKey` (document type *or* element type — Umbraco doesn't distinguish the two at the `IContentType` level, so neither does this; stored as the type's Key, not its alias — §2's correction on why), optional `StartNodeKey`, rules. Not a multi-type list — a second policy record, not a second entry, is how the same type gets a differently-scoped set of rules (§2's SEO-baseline-plus-Blog-Post-refinement example).
- [x] `ContentCheckPolicyRule`: check alias, config, mode (`Advisory` | `Blocking`), `NotEvaluated` policy (`ContentCheckNotEvaluatedPolicy`: `FailOpen` | `FailClosed`).
- [x] **Never the word "section"** for start-node/tree-path scoping (finding M).
- [x] **Resolution service, three responsibilities (§1, §2):**
  - Direct match: given a content item + culture, return policies whose `ContentTypeKey` equals its own document type's Key, filtered by start node.
  - **Composition match (§2):** also return policies whose `ContentTypeKey` names a type this item's type composes from, directly or transitively, walking Umbraco's live composition graph — filtered by the *same* start node check against the item's own location (composition matches run against the item's own snapshot; nothing is nested).
  - **Cascading match (§1):** recursively walk every element-holding property on the item (via the pluggable element-source abstraction — Block List and Block Grid ship built in, on top of Umbraco's own `BlockEditorValues`/`BlockEditorDataConverter` parsing rather than a hand-rolled JSON walk; anything else, including a bespoke or future editor, via a registered source), to any depth, discover each nested element instance, and return policies attached to *that element's* type (direct or composed), paired with a snapshot of that element alone, filtered by start node against the *root* item's location. Each discovered (snapshot, rules) pair is independent — the existing `IContentCheckRunner` ([Core Contract](core-contract-spec.md), unchanged) runs each one exactly as it would run the root document.
  - Aggregation of the resulting per-snapshot reports into whatever [Management API & UI](management-api-ui-spec.md) needs to render — still deferred until that UI is actually being built; `IContentCheckResolutionService.ResolveAsync` returns the flat list of `ContentCheckResolvedTarget`s and stops there.
- [x] **Effective Checks computation (§3), schema-level, no live content required:** given a content type, walk its composition ancestry for direct/composed matches, and its element-holding properties' allowed-element-type configuration (recursively) for cascading matches. Every result carries provenance: Direct, Composition (with the composing type's key), or Cascading (with the property alias and the nested element type's key). The cascading walk's cycle guard is scoped to the current root-to-here path, not "ever visited anywhere" — a diamond-shaped reuse of the same element type via two sibling properties is still reported for both; only a genuine cycle back to an ancestor on the same path is skipped.
- [x] **Do not build composition-only-type detection or a "expand to composing types" picker helper (§2)** — not built, as decided.
- [x] Repository layer internal to a single `ContentCheckPolicyService`/`IContentCheckPolicyRepository` (repo access pattern: nothing outside the service touches the repository directly) — **one deviation from the section headings above:** `ContentCheckPolicy` and `ContentCheckPolicyFolder` share this one repository/service pair rather than each getting its own, since a folder has no lifecycle independent of the policy tree it organizes.
- [x] **`ContentTypeKey` (not alias) is also the right call for [Deploy Integration](deploy-integration-spec.md), not just for rename-safety within one environment.** Stored as designed; the Deploy dependency declaration itself is still Deploy Integration's own, later, phase to build.
- [x] Tests: direct match, composition match (including transitive, two-hop), cascading match at more than one nesting depth, a type governed by two independent policies at once (composition-wide baseline + type-specific refinement, per §2) with no relationship between the records, Effective Checks provenance labeling for all three mechanisms on one type, the cascading cycle guard, and **cascading cost**: a page with N instances of an element type carrying a `Metered` rule is pinned down as exactly N resolved targets in a test — accept-the-cost is the deliberate, visible choice made for v1 (open question 7 in the [Overview](overview.md)), not an accident of traversal order. All against mocked `IContentType`/`IContent`, not a real one — the same real-`IContent` gap [Core Contract](core-contract-spec.md) Phase 1 left open.

**Acceptance:** an editor can create a check policy through the API, attach a required-property check to a document type, and the resolution service returns it for a matching content item — **and**, separately, attach a check to an element type used inside a Block List, and confirm it resolves and runs against every instance of that element found anywhere in the item's property values, at any nesting depth — **and**, attach a policy to a composition, confirm every composing type picks it up automatically (including transitively through a second composition), and confirm the Effective Checks computation correctly labels the provenance of all three kinds of match for a type governed by several policies at once. **Met, against mocked `IContentType`/`IContent`** — no Management API exists yet (that's Phase 3), so "through the API" is exercised as "through `IContentCheckPolicyService`" for now; the real-`IContent` integration-test gap is real, not glossed over (see the Status line above).
