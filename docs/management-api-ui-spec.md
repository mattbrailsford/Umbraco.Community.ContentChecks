# Management API & Backoffice UI

**Status:** Design settled (Phase 3 pre-design, 2026-08-07) the same discipline [Policy Resolution](policy-resolution-spec.md) went through before Phase 2, then **built and manually verified against the demo site (2026-08-07/08)**. Real gaps this doc left as a sketch are now decided: where this even lives in the backoffice (a custom top-level section, not nested in Settings, with a simple welcome dashboard, not an analytics view); the aggregate report shape and its whole-report status (both landed in [Policy Resolution](policy-resolution-spec.md) §6, since the type doing the work is Core, not Web); the live-run mechanism (background-queued, watched over SSE, one mechanism for one item or several); the bulk-run/Backtest/Run-all shape (deferred past v1 — branch/site-wide discovery isn't on the AI-generation loop's critical path, but the mechanism it'll build on is already in place); the Applicable Checks panel replacing what was going to be a separate Effective Checks view plus a separate Results panel (one panel, built on real per-item resolution — see [Policy Resolution](policy-resolution-spec.md) §7); and folder delete-with-children (blocked on non-empty, not cascading). Backtesting (Phase 6) stays explicitly deferred, not part of this build.
**Confirmed working end to end in the browser:** section + welcome dashboard; policy tree with create/rename/delete/move for both policies and folders (root-level create action included); the check policy editor (content-type/start-node pickers, rules-as-a-ref-list with a type-picker → config-modal flow); the Applicable Checks panel's pending rows and its live SSE run, rendering a real result on a real document. **Two things from this doc's own acceptance checklist below are not yet built/verified, recorded here rather than silently dropped:** a click-through from a failed/warned result to the offending property (spec'd, no UI for it yet); and the multi-simultaneous-policy-match scenario (composition-wide + type-specific + cascaded together) rendered with correct provenance in one real panel — the underlying resolution logic for this is unit- and now integration-tested at the Core layer (see [Policy Resolution](policy-resolution-spec.md)), just not exercised end to end through this UI yet.
**Part of:** [Overview](overview.md). Exposes [Core Contract](core-contract-spec.md) and [Policy Resolution](policy-resolution-spec.md); doesn't redefine anything from either.

## Why this isn't optional polish

Check policies are editor-authored, so the UI is the product, not a wrapper around it. No content person is going to hand-edit a DB row to define a rubric.

## Where this lives in the backoffice

**A custom top-level section, not nested inside Settings — decided in the Phase 3 pre-design, not just assumed.** Settings is where Document Type/Data Type configuration already lives, which made it worth checking directly rather than defaulting to "of course this gets its own section." It doesn't fit, for two reasons that both trace back to decisions already made elsewhere in this doc, not new ones invented to justify the choice:

- **This project already committed to check policies being editor-authored** (this page's own opening line). In most real Umbraco installations, ordinary content editors don't have Settings access at all — it's conventionally reserved for developers/admins. Putting policies there would directly contradict a goal already decided, not just be a suboptimal layout.
- **Umbraco's permission model grants access per section**, custom or built-in, with no finer-grained way to expose one tree inside a section while hiding its siblings. A dedicated "Content Checks" section means a content-editor user group can be granted exactly that and nothing else. Nesting inside Settings forces a choice between over-granting Settings access (exposing Document Types, Data Types, everything else there) or building custom permission logic Umbraco doesn't provide for free.

**The honest cost:** one more icon in the section navigation, which the Umbraco ecosystem generally treats as something to avoid doing casually. Not casual here — it's a direct consequence of the editor-authored requirement, not a default reached for out of habit.

**Default dashboard: a simple welcome screen, not a health/analytics view — checked against real precedent, not guessed.** Umbraco.AI's own section dashboard (`Uai.Dashboard.AI`) is exactly this shape: a short "what this does" intro plus one primary button pointing at the first real action a new install needs ("Create a Connection"). Content Checks' own dashboard follows the same pattern — a short intro, one primary button ("Create a Policy"). **Deliberately not** a richer view showing site-wide check status ("N pages currently failing") — that needs the branch/site-wide sweep this doc already deferred past v1; building it now would mean either faking the data or quietly pulling that deferred feature back into scope. Upgrading this dashboard once that sweep exists later is the natural next step, not something v1 needs to solve.

## Management API (`Umbraco.Community.ContentChecks.Web`)

- [x] **Run checks for one or more content items** — not a single blocking call. `POST /evaluation` takes `{ ContentKeys: Guid[] }` (a single key is just the N=1 case, not a separate endpoint) and returns a run id immediately; `GET /evaluation/{runId}/stream` (SSE) and `GET /evaluation/{runId}` (plain poll, fallback) surface progress and each item's `ContentCheckAggregateReport` as it finishes. See "Live-run mechanism" below for the full design and why.
- [x] List/CRUD check policies and their rules (see [Policy Resolution](policy-resolution-spec.md)).
- [x] List registered check *types* with their config schema (`GetConfigSchema()` — see [Core Contract](core-contract-spec.md)) — the UI renders every check's config form from this, no per-type frontend code.
- [x] **Applicable Checks for a content item** — not the schema-level Effective Checks service. Returns `IContentCheckResolutionService.ResolveAsync`'s own output ([Policy Resolution](policy-resolution-spec.md) §7): every target for this real item, each with its `PolicyMatches` (policy, provenance, rules), before anything has run. This is what the per-item panel renders as pending rows; running (above) fills them in. **No dedicated Effective Checks (schema-level, type-only) endpoint in v1** — see §7's reasoning: it answers a different, genuinely useful question, but not one this UI needs answered for v1, and the underlying Core service stays built and tested either way.
- [x] **Tree + folder endpoints** (§"Tree and folders" below): children-of-folder/root, ancestors (breadcrumb), folder create/rename-or-move/delete. Moving a *policy* into or out of a folder is not a separate endpoint — it's the `ParentFolderKey` field on the existing policy update call ([Policy Resolution](policy-resolution-spec.md) §4).
- [x] OpenAPI client generation, matching the Umbraco.AI frontend toolchain (Lit + TS + Vite + @hey-api/openapi-ts).

## Tree and folders

Prompted directly: policies should be organized in a tree, with folders an editor creates, the way Data Types/Document Types/Media Types already work — not the flat list Umbraco.AI's own Profiles/Connections/Guardrails use today (checked directly: none of them have a tree or a folder concept, so they weren't a usable precedent here).

**Real precedent, checked directly, once Umbraco.AI came up empty: Umbraco.Automate's own automation tree.** It solves the identical problem — a custom, EF-backed entity needing folder organization in its own backoffice tree — without using Umbraco CMS Core's native tree/folder base classes (`EntityTreeControllerBase`, `FolderTreeControllerBase<T>`) at all. Its shape, adopted here:

- **Backend:** plain, hand-rolled REST controllers (not the native CMS tree/folder base classes) exposing children-of-root, children-of-folder, ancestors (for breadcrumb), and folder create/update(rename-or-move)/delete. `ContentCheckPolicyFolder` is the data model ([Policy Resolution](policy-resolution-spec.md) §4); moving a *policy* into or out of a folder is just its `ParentFolderKey` field on the normal policy update call, not a dedicated endpoint — same as Automate does for its own automations.
- **Frontend:** rides Umbraco's native tree *contracts* (`UmbTreeDataSource`, `UmbDefaultTreeElement`/`UmbDefaultTreeContext`) against this package's own data source implementation, exactly as Automate's `UaAutomationTreeServerDataSource` does — proving a third-party EF entity can use the native tree UI plumbing without needing the native tree UI's backend base classes to match it.
- **Content Checks' own section root becomes a `kind: "tree"` menu item**, replacing what would otherwise be a flat `entityContainer`/`collection` view (the pattern Umbraco.AI uses, now known not to fit this need).

**Delete-with-children: blocked, not cascading** — decided in the Phase 3 pre-design, see [Policy Resolution](policy-resolution-spec.md) §4. Deleting a non-empty folder is rejected; an editor empties it first. Automate cascades for its own folders, but a check policy governs real publish-blocking behavior, so losing several silently is a bigger footgun here than losing some automations.

## Live-run mechanism

**A run always has one or more items in it — there's no separate "batch" concept.** Sending one content key is just the N=1 case of the same mechanism, not a different endpoint or a different code path. This fell out of asking what an AI agent actually needs: checking a whole Draft Set (several related unsaved items) is really "call the same single-item evaluation once per item, then combine the results" — nothing about that needs branch-walking or a different mechanism, just a caller that already knows which items it cares about.

**Why blocking-and-wait isn't good enough:** the Run button's main real use is checking *unsaved edits while someone's still working* — and content with no saved version never gets a cache hit ([Core Contract](core-contract-spec.md) §5 skips the cache entirely when there's nothing to key on). So several AI-judged rubric checks across a page's nested blocks is the normal case, not an edge case, and that's before even considering more than one item. One blocking HTTP request risks a timeout and gives the editor nothing to look at while it runs.

**Chosen: a background-queued run, watched live over Server-Sent Events.** Considered and rejected: a single blocking request (timeout risk, no feedback); plain polling (works, but once the run-tracking half exists either way, SSE's native browser reconnect/resume makes it more resilient for barely more implementation cost).

- A singleton `IContentCheckRunTracker`, wrapping an in-memory `ConcurrentDictionary<Guid, ContentCheckRunState>`. Web-only, not Core, not persisted — a run still going when the app pool recycles is simply lost, and the caller starts again. No run-history feature is implied by this.
- `POST /evaluation` with `{ ContentKeys: Guid[] }` creates a `runId`, records an initial `Running` state, and **enqueues** the work rather than firing it directly from the request. A bare `Task.Run` inside the handler is a known trap: the request's own DI scope (and anything scoped it was using) gets torn down the moment the response is sent, potentially out from under work that's still running. The queue is a `Channel<Func<...>>` — .NET's own documented "queued background tasks" building block — drained by a dedicated `BackgroundService`, each item processed in a fresh scope it creates itself via `IServiceScopeFactory`, fully decoupled from the request that enqueued it. Returns `{ RunId }` immediately — before any content has been checked.
- **A safety cap on list size, not just a convention:** `POST /evaluation` rejects a list above a fixed limit (recorded as 50 pending real-world tuning), so this endpoint can't quietly become an uncapped sweep just because nothing stops a caller from passing a large list through it. Anything bigger genuinely belongs to the deferred branch/site-sweep case below, once that's built.
- **Concurrency is bounded across items, deliberately, not left to fall out of a loop.** Each item's own evaluation can already fire up to 4 concurrent AI-judged checks internally ([Core Contract](core-contract-spec.md) §4's existing runner cap, unchanged). Running every item in a list fully in parallel on top of that multiplies unpredictably — 5 items in flight at once could mean 20 concurrent AI calls nobody decided on. So items within one run execute with their own small, separate concurrency cap (starting at 2–3 concurrent items), the same bounded-concurrency pattern the runner already uses for AI checks, applied one layer up. This is an approximate ceiling (item-cap × per-item-cap), not an exact one — an exact whole-run cap would mean sharing one limiter across every item's internal check execution, reaching into Phase 1's already-finalized runner internals. Left for a targeted fix later if real usage shows the approximate version isn't tight enough, not solved speculatively now.
- The queued work calls `IContentCheckEvaluationService.EvaluateAsync(..., progress: ...)` ([Policy Resolution](policy-resolution-spec.md) §6) once per item, within that concurrency bound — the same entry point Automate calls in-process for a single item, just with a progress callback Automate never has to pass.
- `GET /evaluation/{runId}/stream` — an SSE (`text/event-stream`) endpoint, one consistent shape regardless of how many items the run has. It emits a progress event every time any target (in any item) finishes; when an item's last target finishes, one more event fires carrying that item's complete `ContentCheckAggregateReport`; when every item is done, a final event closes the stream. A single-item run is just the N=1 case of this same stream — its one "item complete" event is also its final event.
- `GET /evaluation/{runId}` stays too — a plain "current state right now" read of the same tracker, free once it exists, and a fallback if SSE is ever blocked (some proxies still mishandle long-lived connections).
- **Operational note, not a design gap:** whatever sits in front of the site needs an idle-timeout long enough not to kill the stream mid-run — normal for anything already hosting a real Umbraco backoffice, just worth attention at deploy time.

**Deliberately out of scope here: discovering items automatically from a branch or the whole site.** That's a different problem (paged descendant walking, a much larger and open-ended item count) from "the caller already knows which items it wants checked," and it isn't on the AI-generation loop's critical path — Draft Sets are small, bounded sets of known items, not branches to search. See Backtest and the Run-all endpoint below for where that lands instead: later, as a discovery step layered on top of this same run mechanism, not a reason to rebuild it.

## Backoffice UI (`Umbraco.Community.ContentChecks.Web.StaticAssets/Client`), Lit + TypeScript

- [x] **Policy tree** — replaces a flat list as the section's root view (above): folders and policies as sibling nodes, create/rename/move/delete folder from the tree's own context menu, a move dialog (Umbraco's native `moveTo` tree-picker) to re-parent a policy or folder — drag-and-drop wasn't built, the move dialog covered it more cheaply.
- [x] **Check policy editor** — a dedicated workspace: name/alias, a content-type picker (one type — doc type or element type, see [Policy Resolution](policy-resolution-spec.md)), an optional start-node picker, add rules from the registered-type list, per-rule config form (`cc-model-editor`, ported per [Core Contract](core-contract-spec.md) — no bespoke form per check type), mode toggle (Advisory/Blocking), `NotEvaluated` fail-open/fail-closed toggle. Built as a ref-node list with a type-picker → config-modal flow, matching Umbraco.AI's Guardrails/context-resources pattern rather than inline expanding rows.
- [ ] **Applicable Checks panel**, embedded in the content app (property-editor-adjacent, not a separate section) — one panel, not two, settled after asking why a "what applies and why" view and a "what happened when it ran" view would ever need to be different screens ([Policy Resolution](policy-resolution-spec.md) §7):
  - [x] **Before running:** calls the Applicable Checks endpoint (above), renders one row per resolved policy match, grouped by provenance (Direct / Via composition `[X]` / Via nested element `[Y]` in property `[Z]`) — verified with a single Direct match against a real document; multiple simultaneous different-provenance matches in one panel not yet verified.
  - [x] **After running (the Run button):** watches the live-run endpoint over SSE (via the generated fetch client, not a native `EventSource` — that can't carry the `Authorization` header this API requires) and updates each row in place as its result comes in — status badge, message. **Not built:** score-vs-threshold bar (no check emits a score yet — Phase 5), and click-through straight to the offending property/element/variant via its `Path`.
  - [x] Rows only ever move from pending to a real result — the "shows up but doesn't apply here" state a schema-level view would need doesn't exist, because everything shown was already confirmed to apply by real resolution.
- [ ] **Health-check-style dashboard** — **deferred past v1**, not part of the Phase 3 build. Run a check policy across a branch/tree, see the status distribution. Needs branch/site item-discovery (see Backtest and Run-all below), which is a genuinely separate, larger problem from the live-run mechanism above and isn't on the AI-generation loop's critical path.
- [x] Component export convention: everything through `index.ts`/`export.ts`, never import by path (per repo CLAUDE.md lesson).

**Acceptance:** an editor with no dev involvement can create a check policy, attach a required-image check and a stub rubric check to a doc type, open a real page of that type governed simultaneously by a composition-wide policy, a type-specific policy, and a cascaded element-type policy, see the Applicable Checks panel list all three as pending with correct provenance *before* running anything, then run it and watch each row fill in with its real result, with a click-through to the missing property — **and** can create a folder, move an existing policy into it, and see the tree reflect both without a page reload.

**Partially met (2026-08-08):** the create-policy/attach-a-rule/run-it/see-a-real-result path is verified end to end, and the folder create-move-tree-reflects-live path is verified end to end. **Not yet verified:** the three-simultaneous-policy-match scenario in one panel, and the click-through to the missing property (not built at all yet).

## Backtest (Phase 6) and the Run-all endpoint — deferred past v1, mechanism reserved

Settled in the Phase 3 pre-design conversation: both of these need *discovering* items from a branch or the whole site (paged descendant walking, an open-ended and potentially large count), which is a genuinely different, larger problem from "Live-run mechanism" above, where the caller always already knows exactly which items it wants checked. Neither is on the AI-generation loop's critical path — Draft Sets are small, bounded, known sets of items, not branches to search — so neither is part of the Phase 3 build. Recorded here so the shape isn't lost, not scheduled.

**Backtest** — the thing that makes rubrics trustworthy (finding K in the [Overview](overview.md)); small, high-value, easy to skip and shouldn't be, whenever it does get built:
- Run one specific check policy (the one someone's currently editing) across an existing content branch, show the status distribution. Surfaced in the check policy editor as "test this against your real content."
- Rationale: if a new rubric fails 90% of the live site, the rubric is wrong, not the site. Without this, checks get authored blind and abandoned.
- Needs a narrower per-item call than Run-all below: only the content this *one* policy's content type reaches (direct, composed, or cascaded — the same matching [Policy Resolution](policy-resolution-spec.md) already does, just scoped to one policy instead of every applicable one), not everything `IContentCheckEvaluationService.EvaluateAsync` would otherwise resolve.

**Run-all** — raised alongside [open question 5](overview.md): not "should one check be able to see the whole site" (that's [Core Contract](core-contract-spec.md)'s `Scope` cut, still genuinely undecided as a check-authoring question — a single check's `EvaluateAsync` still only ever sees one snapshot), but a simpler, purely operational ask: run *every* applicable policy across a branch or the whole site in one sweep, rather than one named policy at a time the way Backtest is scoped.
- Unlike Backtest, this needs no new per-item matching logic at all — it's `IContentCheckEvaluationService.EvaluateAsync`, unchanged, called once per discovered item, exactly like the Live-run mechanism already does for an explicit list.
- **The version-keyed cache ([Core Contract](core-contract-spec.md) §5) is what makes this affordable to actually run on a schedule**, not just on demand: a repeat sweep only pays for items that changed since the last one, so "run all checks across the site" degrades gracefully from "expensive full audit" the first time to "cheap incremental check" every time after — without this endpoint needing any cache-awareness of its own, since that's the underlying `IContentCheckResultCache`'s job regardless of caller.

**Both, whenever built, are a branch-discovery step layered on top of the same Live-run mechanism above** — paged descendant walking feeding items into the same run/tracker/stream machinery, plus their own bounded item-discovery-and-throughput concerns (how many *discovered* items run concurrently, likely tighter than the small explicit-list cap above, given the count here is open-ended rather than a bounded caller-supplied list). Not solved now — recorded so the later work has a clear seam to build on, not a reason to touch the mechanism above.

## Property-targeted check config base class + content-type-aware property picker — deferred, no blocking gap

Raised while reviewing the shipped rules editor (below): `RequiredPropertyCheck`'s config (`RequiredPropertyCheckConfig.PropertyAlias`) is a plain text field today — an editor has to know and type the exact property alias by hand, and every future property-targeted check would redeclare the same field from scratch. **Deferred rather than built now**, because `RequiredPropertyCheck` lives in `Checks/Examples/` and is explicitly a proving check, not a real one — there's only one property-targeted check to design this against, and building shared infrastructure against a single throwaway example risks guessing the wrong shape. Revisit once a second, real property-targeted check exists.

**No Core or attribute change is needed to unblock this later — the extension point already exists.** `ContentCheckFieldAttribute` already carries `EditorUiAlias`/`EditorConfig`, so pointing a config field at a custom picker instead of the default text box is already supported; nothing about deferring this closes off the option or requires a migration.

**The shape when it does get picked up:**

1. **A shared base config class** (e.g. `PropertyTargetedCheckConfig`), giving check authors a `PropertyAlias` property already decorated with the right `EditorUiAlias`, so they inherit/compose it instead of redeclaring `[ContentCheckField(...)]` by hand on every property-targeted check.
2. **A new frontend property editor UI** (e.g. `ContentChecks.PropertyEditorUi.PropertyAliasPicker`) rendering an actual property picker — scoped to the policy's own selected content type's real properties — instead of a free-text alias box a typo can silently break.
3. **How it discovers the content type, decided and verified, not just assumed:** not by threading `contentTypeKey` as explicit `data` through the rule type-picker modal → config modal → `cc-model-editor` → this one field's editor. `UmbModalManagerContext.open(host, ...)`'s own doc comment states the `host` passed in "acts as the modal origin for the context api" — confirmed by reading the real source, not assumed — so a context provided at the policy workspace level stays reachable from inside stacked modals even though the modals themselves render into a separate overlay container. The picker can `consumeContext(CONTENT_CHECKS_POLICY_WORKSPACE_CONTEXT, ...)` directly, the same mechanism the policy workspace editor element itself already uses, and read `.model.contentTypeKey` off the live workspace context with no prop-drilling.
4. It would then query that content type's own properties (the same document-type item lookup the existing content-type picker already triggers) to populate its option list, filtered to only the properties that content type actually has.

**Considered and rejected: splitting "target" out of the rule model as a first-class, cross-cutting concept** (e.g. `Rules: TargetGroup[] -> Rule[]` instead of a flat `Rule[]`, so several rules against the same property share one target selection). Rejected for now on two grounds: not every check is property-scoped — a property alias is just a config field on the checks that happen to need one (like `required-property`), not a concept the whole check model is built around, so forcing every check into "targets a property" is a real constraint on future check authors, not a free abstraction. And the expected number of rules stacked on the *same* property within one policy is probably low (most real policies are likely to span different properties/checks rather than pile several rules onto one), so the re-picking friction this would solve is probably minor UX cost, not a workflow blocker. If it turns out to matter in practice, a cheaper fix than restructuring the model is UX-only: pre-fill a new rule's `propertyAlias` from the last rule added in the same policy.
