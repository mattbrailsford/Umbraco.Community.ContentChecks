# Triggers — when checks run

**Status:** **Reopened 2026-08-11 — the design below is being reshaped and two of its stated facts are now known false.** Measuring the publish path directly (`PublishNotificationVersionIdentityTests`, Tests.Integration) disproved "every publish is also a save" (see the correction in the on-save section), and surfaced a defect in [Core Contract](core-contract-spec.md) §5's result cache that this phase would inherit. **The Phase 1 cache fix lands before any Phase 4 code.** The open reshape, still being discussed and not yet written down as settled: dropping the on-save auto-run entirely, and turning the publish gate from "evaluate `Free` rules inline" into "look for a completed run matching the content as it stands, and let each rule's existing `NotEvaluated` fail-open/fail-closed setting decide what happens when there isn't one" — which, if it holds up, lifts the `Free`-cost restriction on blocking and lets `Metered`/AI-judged checks gate a publish without ever running inline. Treat everything below as the prior design plus corrections, not as current intent. **Confirmed 2026-08-12, from the opposite direction:** [Guard](guard-spec.md)'s own correction — a run's stored report must never be user-specific — requires exactly this "read a stored run" shape anyway, since deciding whether a `Fail` blocks *this* publisher has to happen after the run, against the report it produced, never inline as part of running it. The publish-gate handler this doc still hasn't built is the one place `ContentCheckResponse` gets resolved, for the real publishing user, against the stored report's `RequirementLevel`s — not `Mode`/`Blocking`, which no longer exists on the rule.

**Status (prior):** Design settled (Phase 4 pre-design, 2026-08-08), the same discipline [Core Contract](core-contract-spec.md), [Policy Resolution](policy-resolution-spec.md), and [Management API & UI](management-api-ui-spec.md) went through before their own phases — not yet built. ## No existing precedent to build on — checked, not assumed

Umbraco.AI's Guardrails feature was the obvious place to look for prior art (this project has leaned on Umbraco.AI as real precedent throughout). It turns out to have none for this specific problem: Guardrails is an `IChatClient` middleware pipeline wrapping AI chat calls, blocking by throwing an exception inside that pipeline — it never subscribes to, cancels, or otherwise touches `IContentService`'s save/publish notifications. A repo-wide search for `ContentSavingNotification`/`ContentPublishingNotification`/`ContentSavedNotification`/`ContentPublishedNotification` across both this project and the whole Umbraco.AI monorepo returns zero hits outside `Umbraco.Cms` itself. This project is the first to wire a content-quality gate into the real CMS publish pipeline here — the design below is built from Umbraco's own notification mechanism directly, not adapted from a sibling's solved problem.

## The real mechanism

Four notifications matter, all in `Umbraco.Cms.Core.Notifications`:

| Notification | Cancelable? | Fires |
|---|---|---|
| `ContentSavingNotification` | Yes | Before a save commits |
| `ContentSavedNotification` | No | After a save has committed |
| `ContentPublishingNotification` | Yes | Before a publish commits (fired once per content item, inside the same commit path every publish goes through — see below) |
| `ContentPublishedNotification` | No | After a publish has committed |

Cancellation is `ICancelableNotification.Cancel` (a plain bool), with a convenience method on the base class every one of these actually uses:

```csharp
public void CancelOperation(EventMessage cancelationMessage)
{
    Cancel = true;
    cancelationMessage.IsDefaultEventMessage = true;
    Messages.Add(cancelationMessage);
}
```

Handlers are `INotificationAsyncHandler<T>`, registered via `builder.AddNotificationAsyncHandler<ContentPublishingNotification, MyHandler>()` in the Composer — no existing pattern for this in this project yet, established fresh here. `EventAggregator.Publish` dispatches to async handlers and blocks the calling thread on their `Task` before reading back `Cancel` — meaning `await`ing `IContentCheckEvaluationService.EvaluateAsync(...)` from inside a handler is fully supported, not a hack, but it **synchronously holds the publish call open for as long as that await takes.** Nothing in this pipeline imposes a timeout on that wait.

**How the cancellation reason actually reaches the editor — reusing Umbraco's own plumbing, not inventing a new one.** The lesson this whole section exists to satisfy (see [research.md](research.md), Contentful's `setInvalid()` gap): a check that only shows a red badge but doesn't actually gate the publish action is a worse UX than no check at all — it looks like protection and isn't. Every `Blocking` entry has to wire into the real publish pipeline, never just a UI-layer flag, and the reason it fails has to reach the editor, not just a generic "blocked" state. The Management API's generic `ProblemDetails` response for a notification-cancelled publish carries only a fixed title/detail (`"Publish cancelled by event"`) — on its own, that's exactly the same trap: a red badge with no reason. The actual "why" channel is separate: `CancelOperation`'s `EventMessage` gets appended to the request's ambient `EventMessages`, every Management API controller is decorated `[AppendEventMessages]`, and that filter serializes every accumulated message into an `Umb-Notifications` response header. The backoffice's own HTTP interceptor (`api-interceptor.controller.ts`) already reads that header on every response and shows each message as a toast — this is wired in globally, not something a plugin has to build. So a blocking check handler gets a real, editor-visible reason for free, just by calling `CancelOperation(new EventMessage("Content Checks", "<why>", EventMessageType.Error))` — no new frontend work needed for the notification itself.

## On-save: an implicit trigger for the existing run mechanism, not a new one

**Hooks `ContentSavedNotification` (non-cancelable), not `ContentSavingNotification`.** Advisory-only isn't just a policy choice enforced by convention — using the non-cancelable, after-the-fact notification makes it structurally true: there is no `Cancel` property to (mis)use, so a future change to this handler literally cannot make on-save blocking by accident.

**No new run mechanism.** The handler does exactly one thing: enqueue the content item onto the *same* background-queued run the Management API's `POST /evaluation` already uses ([Management API & UI](management-api-ui-spec.md)'s "Live-run mechanism"), fire-and-forget. The Applicable Checks panel already watches a run over SSE; an editor who saves now sees their pending rows start filling in without having clicked "Run checks" themselves. This is the whole reason that mechanism was built as "always background-queued, one item or several" rather than tied to a button — on-save is just another caller of it, not a reason to build a second one.

~~**Redundant runs are cheap, not a new cost to design around.** Every publish is also a save (`ContentSavingNotification`/`ContentSavedNotification` fire on the publish path too, since Umbraco always saves as part of publishing) — so a publish will trigger both the on-publish blocking check (below) and this on-save auto-run.~~

**Corrected 2026-08-11 — measured, and it's false.** `PublishNotificationVersionIdentityTests.VersionId_AcrossSaveAndPublish` (Tests.Integration, `Triggers/`) captures every content notification fired during `IContentPublishingService.PublishAsync` on an already-saved item. Only two fire: `ContentPublishingNotification` and `ContentPublishedNotification`. **No save notification fires on the publish path at all.** The paragraph above assumed otherwise and was never checked.

Two things that were leaning on it, now unsupported:

- **A publish does not get a full advisory run "for free" via the on-save handler.** If a publish should produce a complete report (every rule, not just the gate's narrow subset), the publish handler has to start that run itself. This is the whole reason the design below moves to reading a *stored* run rather than assuming a parallel one is happening.
- **The cache-overlap argument was doubly wrong** — it also relied on `VersionId` as a freshness key, which [Core Contract](core-contract-spec.md) §5's defect box now shows doesn't work. Both halves of the sentence were wrong for independent reasons.

What the same test *does* confirm, and what the stored-result gate depends on: at `ContentPublishingNotification` the item still carries the version id its saves produced (`versionId=1`), moving to a new version only once the publish commits (`versionId=2`, with `publishedVersionId=1`). So a run recorded against the content as the editor last saved it is genuinely matchable at gate time — there is no "publish always fails the first time" problem.

**One knob, not a suggestion:** a site-level setting to disable on-save auto-triggering entirely, defaulting on. Explicit `Save` clicks in the backoffice aren't continuous (no per-keystroke autosave to worry about), but a site with several `Metered` AI-judged checks attached to a high-traffic content type could still find automatic evaluation on every save an unwanted cost; this is the same instinct as the Management API's own run-size safety cap (a real cap, not just documented advice).

## On-publish: a new, narrow, synchronous blocking path

**Hooks `ContentPublishingNotification` (cancelable).** Unlike on-save, this handler runs checks *inline*, synchronously, inside `HandleAsync`, and calls `CancelOperation(...)` if a `Blocking`-mode rule fails. It deliberately does **not** go through the queue/tracker/SSE mechanism on-save and on-demand use — that machinery exists to stream progress for a run an editor is watching; a publish-gate needs one synchronous pass/fail answer in the same HTTP response, not something to subscribe to.

**Restricted to `Free`-cost, `Blocking`-mode rules only — this is the actual enforcement of "no `Metered`/AI-judged check gates a publish click."** [Core Contract](core-contract-spec.md)'s runner has no timeout or budget anywhere (checked directly — the only time-tracking in `ContentCheckRunner` is a `Stopwatch` used purely for reporting, never to cancel anything), and the CMS notification pipeline itself imposes none either. Without a cost restriction, a slow AI-judged check would genuinely hang a publish click for however long that call takes, with nothing anywhere in the stack stepping in. Rather than inventing a request-scoped timeout budget that doesn't exist today, on-publish blocking is scoped down to the check tier that's contractually meant to be fast and deterministic. A `Metered` rule can still be attached to the same policy and still run — via on-save (advisory) and on-demand — it just never participates in the publish gate. This also naturally bounds the cost of a branch/bulk publish of many items each running the gate (see below), since `Free` checks are cheap by contract in a way `Metered` ones aren't.

## What we can and can't detect

**Single-item vs. branch/bulk publish: cannot be detected at the notification layer — checked directly, not assumed away.** `ContentPublishingNotification`'s underlying commit path (`CommitContentChangesInternal`) takes and fires the notification for exactly one content item per call, every time, regardless of whether the top-level caller was `IContentPublishingService.PublishAsync` (single item) or `PublishBranchAsync` (branch/bulk) — so from inside the handler, a 50-item "Publish with descendants" looks identical to 50 independent single-item publishes: 50 separate notification firings, one item each. There is no count, batch id, or "part of a branch operation" flag on the notification to key off. **This is why the actual enforcement above is the `Free`-cost restriction, not caller detection** — it can't be caller detection, because the signal doesn't exist.

**Scheduled/background publishes: a plausible signal, not a verified one — flagged as an assumption to confirm when this is built, not shipped on faith.** Scheduled publish calls `IContentService.PerformScheduledPublish` from a recurring background job, with no live HTTP request behind it; `PublishBranchAsync(..., useBackgroundThread: true)` likewise runs inside a background task rather than the original request. Both cases plausibly mean `IHttpContextAccessor.HttpContext` is `null` inside the handler for these paths, giving a clean way to skip blocking entirely (treat as advisory, same as on-save) whenever there's no live request. This wasn't traced deep enough into `ILongRunningOperationService`'s execution context to state as fact — verify this empirically (a scheduled-publish integration test asserting the gate never fires) before relying on it, rather than assuming the inference holds.

**Interactive human vs. a scripted API client hitting the same single-item publish endpoint: genuinely indistinguishable, and not solved here.** Both go through the exact same `PublishDocumentController.Publish` → `IContentPublishingService.PublishAsync` → `ContentPublishingNotification` path with a live `HttpContext`, authenticated the same way a real backoffice session is (nothing on the notification marks "this came from a human click" vs. "this came from a script using the same session"). The only inference available — inspecting `HttpContext.User`'s authentication scheme (`UmbracoBackOffice`/`UmbracoBackOfficeToken` vs. some other client-credentials flow) — is out of scope to build for v1, matching the existing exclusion of "API-driven publishing" from blocking. Documented as a real limitation, not presented as solved by the `HttpContext`-null check above (that check only catches *background-job-originated* publishing, not a third-party system calling the Management API directly over HTTP).

## Explicitly out of scope for blocking in v1

This is [finding E](overview.md#3-interrogation-findings-master-reference) from the master interrogation-findings table: non-interactive publish paths (scheduled, bulk, descendants, Deploy) get explicit per-trigger opt-in, never blocking. Scheduled publishing, bulk publish, publish-with-descendants, Umbraco Deploy transfers, API-driven publishing all record a report where checks are configured (via the on-save-style fire-and-forget trigger, not the publish gate), but never block. Rationale unchanged from the original finding: there is no human to read the feedback, and an LLM round trip inside a 3am scheduled publish is indefensible. **This doesn't mean these scenarios have no path to control** — see [Automate Integration](automate-integration-spec.md): a site owner can wire up deliberate behavior for exactly these moments (notify, escalate, branch) through Umbraco.Automate, without ContentChecks inventing bespoke automation logic for each one.

## Considered and rejected

- **Hooking `ContentSavingNotification` (cancelable) for on-save, and just never calling `CancelOperation`.** Works, but makes "advisory only" a convention someone could accidentally break later, not a structural fact. `ContentSavedNotification` has no `Cancel` property to misuse in the first place.
- **Routing on-publish blocking through the same background-queued/SSE mechanism as on-demand and on-save.** That mechanism's whole shape — return a run id immediately, watch progress — is wrong for a publish gate, which needs one synchronous answer in the same response, not something to subscribe to after the fact.
- **Trying to detect single-item vs. branch publish some other way** (e.g., wrapping/decorating `IContentPublishingService` instead of hooking the notification). Rejected because it means depending on internal CMS service resolution order/DI decoration rather than the public notification contract, for a signal that — per the direct source read above — doesn't exist at the notification layer regardless of how it's intercepted; `CommitContentChangesInternal` itself only ever sees one item at a time no matter which top-level method invoked it.
- **A request-scoped timeout wrapped around the publish-gate's evaluation call** (e.g., `Task.WhenAny(evaluate, Task.Delay(budget))`), to allow `Metered` checks to participate in blocking as long as they finish quickly. Rejected for v1: it reintroduces exactly the risk the cost-tier restriction already avoids for free (a check that's slow *this once* — a cold AI provider, a network hiccup — either silently passes past its budget with no evaluation, or blocks the publish anyway once it's already run long enough to be indistinguishable from hanging), and there's no existing budget/timeout concept anywhere in [Core Contract](core-contract-spec.md)'s runner to hang this off. Restricting to `Free`-cost checks is the simpler, already-correct-by-contract answer; revisit only if a real `Metered` check needs to gate publishes and the cost-tier restriction turns out to be too blunt.

## Phase 4 — build checklist

- [ ] `INotificationAsyncHandler<ContentSavedNotification>` — enqueues the saved content onto the existing run tracker (fire-and-forget), gated by the site-level "auto-run on save" setting (default on).
- [ ] `INotificationAsyncHandler<ContentPublishingNotification>` — resolves applicable policies for the content, evaluates only `Free`-cost/`Blocking`-mode rules synchronously, and calls `CancelOperation` with one combined `EventMessage` summarizing every failing rule if any fail. Skips entirely (no evaluation, no blocking) when `IHttpContextAccessor.HttpContext` is `null` — verify this genuinely excludes scheduled/background-thread branch publishes before relying on it, per the note above.
- [ ] Composer wiring: `builder.AddNotificationAsyncHandler<...>` for both, following the pattern established here since none exists yet in this project.
- [ ] The site-level "auto-run checks on save" toggle (Web/config layer, not Core — this is a deployment knob, not a check-authoring concern).
- [ ] Integration test asserting a scheduled publish (via `IContentService.PerformScheduledPublish`, not the Management API) never triggers the publish-gate handler's blocking path — the one empirically-unverified assumption this design rests on.
- [ ] Integration test asserting a `Metered` rule on a policy is present in the resolved targets but never evaluated or considered by the publish-gate handler, only by on-demand/on-save runs.
- [ ] Integration test asserting a blocked publish surfaces its `EventMessage` via the `Umb-Notifications` header — the exact mechanism the frontend already reads, not a new one this project has to build.

**Acceptance:** an editor with a `Blocking`, `Free`-cost rule attached (e.g. required-property) clicks "Save and publish" on a page missing that property, sees the publish rejected with a specific, readable reason (not a generic "cancelled by event" toast) naming the failing check, and after adding the value, publishes successfully. Saving a draft (not publishing) with the same missing property never blocks and never shows an error toast — it silently kicks off a check run the editor can see fill in on the Applicable Checks panel if they look. A `Metered` rubric check attached to the same policy is visibly listed as an applicable check on the item, but is never evaluated as part of either the save or the publish action — only via on-demand "Run checks" or the same background auto-run on-save triggers.
